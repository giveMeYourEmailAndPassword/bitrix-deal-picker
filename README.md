# Bitrix24 Deal Picker

Приложение «Получить заявку» для Bitrix24. Оно показывает менеджеру самую
старую подходящую входящую сделку, проверяет его навыки и, только когда запись
явно разрешена, назначает менеджера ответственным.

Новая установка всегда начинается в безопасном режиме:

- `DRY_RUN=1` — Bitrix24 не изменяется;
- `GREETING_AUTO_SEND=0` — сообщения клиентам не отправляются;
- пользователь подтверждается сервером через Bitrix24 `user.current`;
- выдача разрешена только активному внутреннему сотруднику (`UF_DEPARTMENT`) с
  явно сохранённым администратором правилом доступа;
- домен портала и браузерные origins ограничены allowlist;
- состояние хранится транзакционно в SQLite на Railway Volume;
- Railway включает релиз только после успешного `/api/ready`.

После контролируемой проверки прав `GREETING_AUTO_SEND=1` включает фоновое
приветствие. Кнопка менеджера не ждёт историю чата: сначала Bitrix подтверждает
ответственного, стадию и маркер операции, приложение фиксирует claim, а затем
durable outbox резервирует ровно эту операцию. Короткоживущий фоновый поток
сначала вызывает `imopenlines.operator.answer`, затем отправляет сообщение через
`im.message.add` с OAuth взявшего заявку менеджера. OAuth-токен не записывается
в SQLite или логи; после начала отправки автоматического повтора нет.

## Как устроено

```text
Bitrix24 iframe
    │ OAuth-контекст текущего пользователя
    ▼
Python HTTP service
    ├── проверка portal domain + user.current
    ├── поиск и повторная серверная проверка сделки
    ├── request/rate/cache limits
    └── события claim/reject/greeting + access rules
                         │
                         ├── /data/state.sqlite3 + durable outbox
                         │     Railway Volume
                         └── signed HMAC events/requests ──► База
```

`BITRIX_WEBHOOK_BASE` используется только на сервере и никогда не передаётся
браузеру. Перед записью сервер заново получает пользователя и сделку из
Bitrix24; полям `currentUserId`, `managerId` и копии сделки из браузера доверять
нельзя. Выбранная сделка связывается с пользователем короткоживущим подписанным
серверным токеном. Он фиксирует ID пользователя, версию сделки и текущую
политику выдачи: навыки, active/intranet-статус, включённость правила и дневной
лимит. Если что-либо из этого изменилось, старый выбор отклоняется и сделку
нужно получить заново. Срок токена задаёт `SELECTION_TOKEN_TTL_SECONDS` (по
умолчанию 1800 секунд).

Незавершённая операция после `CLAIM_OPERATION_PENDING_TTL_SECONDS` (по умолчанию
300 секунд) сверяется с Bitrix. Точное совпадение маркера подтверждает запись и
позволяет восстановить claim event; точно неизменившаяся исходная сделка
освобождает неисполненную попытку. Любое неоднозначное состояние остаётся
заблокированным для ручной проверки администратором. Фоновая сверка сама
никогда не меняет Bitrix24. При восстановлении событию присваивается время
резервирования соответствующей попытки, а не позднее время повтора или фоновой
сверки. Для новых операций это явно сохранённый `attemptStartedAt`; для старых
совместимых строк используется ближайшая сохранённая временная метка операции.
Поэтому восстановление не переносит событие на дату запуска сверки.

Статистика `CLAIM_STATS_SOURCE=app_events` считается по неизменяемым событиям
принятия заявки, записанным приложением. `DATE_MODIFY` и простое нахождение
сделки в стадии `NEW` не считаются достоверной датой принятия. Ручной переход
в Bitrix24 вне приложения не создаёт такого события и в эту статистику не
попадает.

## Дополнительная заявка через «Базу»

Интеграция выключена по умолчанию (`EXTRA_CLAIM_REQUESTS_ENABLED=0`). После
одновременного выпуска совместимого backend «Базы» менеджер, исчерпавший
дневной лимит, видит кнопку **«Запросить ещё 1 заявку»** и обязательно пишет
причину длиной 10–500 символов. Одна активная заявка на сотрудника и рабочую
дату сохраняется локально до сетевого вызова, поэтому двойной клик или
перезапуск не создают дубль. После отказа или использования разрешено создать
новый запрос в тот же день.

«База» возвращает одобренное одноразовое разрешение. Приложение атомарно
резервирует его вместе с `claim_operation`, расходует только после проверенной
записи в CRM и финального claim event, освобождает при доказанной ошибке до
записи и удерживает при неопределённом результате до сверки с Bitrix. В
`DRY_RUN=1` разрешения не резервируются, тестовые события не экспортируются и
интерфейс не открывает карточку сделки, потому что ответственный в CRM не
менялся.
Воскресенье и свободное окно 18:00–21:30 работают как прежде и не требуют
дополнительного разрешения.

Для выдачи сверх лимита приложение запрашивает актуальные разрешения перед
поиском и ещё раз непосредственно перед локальным резервированием/записью в
Bitrix. Если «База» недоступна либо разрешение отозвано, истекло или уже
использовано, CRM не меняется. Обычная выдача в пределах лимита от доступности
«Базы» не зависит.

Каждое настоящее событие получает постоянный `eventUuid` и в одной SQLite-
транзакции ставится в `integration_outbox`. Миграция schema v1 → v2 присваивает
UUID старой истории и ставит её в тот же outbox ровно один раз. Событие,
расходующее дополнительное разрешение, отправляется раньше следующего запроса
этого типа; затем запросы менеджеров имеют приоритет над несвязанным
историческим экспортом. Синхронный UI отправляет только конкретный запрос
менеджера; claim backlog обрабатывает фоновый worker, поэтому недоступность
«Базы» не ломает обычную выдачу в пределах лимита и не блокирует очередь после
восстановления связи.

Сервисные POST-маршруты «Базы»:

- `/integrations/deal-picker/v1/extra-claim-requests`;
- `/integrations/deal-picker/v1/grants/query`;
- `/integrations/deal-picker/v1/claim-events`.

Тело кодируется каноническим JSON. Заголовки
`X-Krugosvet-Key-Id`, `X-Krugosvet-Timestamp`, `X-Krugosvet-Nonce` и
`X-Krugosvet-Signature` подписывают строку
`timestamp\nnonce\nMETHOD\nPATH\nsha256(body)` через HMAC-SHA256. Секрет
никогда не попадает в браузер. Transport/429/5xx и HMAC-ответ 409
`replay_detected` повторяются тем же телом с новой подписью и exponential
backoff; постоянный 4xx остаётся в dead-letter аудите. Ответ 409
`active_request_exists` с валидным текущим запросом принимается как
восстановление состояния, если этот remote ID не принадлежит предыдущему
локальному запросу. `idempotency_conflict` и `grant_unavailable` никогда не
считаются успешным дублем и сохраняются для ручной сверки.

## Файлы

```text
app.py                       HTTP/UI и интеграция с Bitrix24
state_store.py               SQLite, транзакции и legacy JSON migration
managers.json                только отключённый обезличенный seed-пример
entrypoint.sh                подготовка Volume и сброс привилегий
Dockerfile                   Python 3.12 runtime
railway.json                 build + readiness healthcheck
.env.example                 полный безопасный шаблон переменных
.github/workflows/test.yml   CI-проверки PR и push
```

Настоящие имена, Bitrix user ID и навыки сотрудников не коммитятся. Основной
и единственный production-источник навыков — поле сотрудника `UF_SKILLS` в
Bitrix24. `/data/managers.json` остаётся отключённым seed-примером. Локальный
fallback из этого файла разрешён только на loopback в сочетании
`DRY_RUN=1` + `ALLOW_UNVERIFIED_USERS=1`; не загружайте production-список
сотрудников на Volume.

## Проверки перед PR

Нужен Python 3.12. Внешних Python-зависимостей у приложения нет.

```bash
python3 -m unittest discover -s . -p 'test*.py' -v
python3 -m py_compile app.py state_store.py
python3 -m json.tool railway.json >/dev/null
python3 -m json.tool managers.json >/dev/null
sh -n entrypoint.sh
sh -n .env.example
git diff --check
```

GitHub Actions выполняет те же проверки на каждом PR и push, затем собирает
Docker-образ, поднимает настоящий HTTP-сервис с root-owned тестовым Volume,
проверяет `/api/ready`, UID/GID 10001, права state-файлов и повторный запуск с
того же Volume.

`ROUTING_POLICY_VERSION` в `app.py` — обязательная версия правил маршрутизации,
а не переменная Railway. При любом изменении логики, способной поменять
допустимость или приоритет сделки для менеджера (стадии, разбор навыков,
классификация, matching или порядок выбора), разработчик обязан увеличить эту
версию. Тогда выпущенные до релиза selection tokens и search cursors сразу
станут недействительными и не применят старое решение к новой логике.

## Локальный read-only запуск

1. Скопируйте `.env.example` в игнорируемый Git файл `.env.local`.
2. Замените только placeholder-значения. Реальный webhook не показывайте в
   терминальных логах и не коммитьте.
3. Оставьте `DRY_RUN=1`, `GREETING_AUTO_SEND=0` и
   `ALLOW_UNVERIFIED_USERS=0`.
4. Для localhost поменяйте `HOST`, `PUBLIC_APP_URL`, `APP_ALLOWED_ORIGINS` и
   каталог состояния:

```bash
HOST=127.0.0.1
PUBLIC_APP_URL=http://127.0.0.1:3000
APP_ALLOWED_ORIGINS=http://127.0.0.1:3000
APP_DATA_DIR=work/local-data
REQUIRE_LEGACY_MIGRATION=0
```

Значение migration `0` здесь допустимо только потому, что это новый локальный
каталог без старой рабочей истории. Для проверки реального переноса оставьте
`1` и положите в каталог полный manifest из четырёх legacy JSON.

5. Загрузите переменные и запустите приложение:

```bash
set -a
. ./.env.local
set +a
python3 app.py
```

Проверка: `http://127.0.0.1:3000/api/ready`. Не используйте
`ALLOW_UNVERIFIED_USERS=1` для проверки production-поведения: этот режим
предназначен только для изолированной локальной отладки и не должен работать
на публичном bind.

## Railway: безопасный первый деплой

Railway запускает Dockerfile. Поле **Custom Start Command** в настройках
сервиса должно быть пустым. В `railway.json` `startCommand` явно задан как
`null`: для этого deployment config-as-code переопределяет возможное старое
значение из Dashboard, но само поле Dashboard не изменяет. Тогда Docker-образ
использует `ENTRYPOINT`/`CMD`; custom start command заменил бы entrypoint и
пропустил подготовку Volume.

### 1. До деплоя

1. Зафиксируйте ID текущего успешного deployment и экспортируйте список
   переменных без публикации секретных значений.
2. Создайте Railway backup существующего Volume. Не нажимайте **Wipe Volume**.
3. Создайте отдельный новый входящий webhook Bitrix24 и сохраните его URL
   только в Railway Variables. Старый webhook пока не отзывайте: он нужен
   текущему deployment и для контролируемого rollback до завершения read-only
   проверки.
4. Убедитесь, что CI зелёный и изменения идут через отдельную ветку/PR. IT
   должен один раз включить для `main` GitHub ruleset/branch protection с
   обязательным PR и обязательным status check этого workflow; сам YAML не
   запрещает прямой merge при красном CI.
5. Проверьте, что у всех менеджеров, которым нужна выдача, заполнено актуальное
   поле `UF_SKILLS` в Bitrix24: production больше не берёт навыки из локального
   `managers.json`.
6. В нужной воронке Bitrix24 сверьте portal-specific коды стадий с кодом:
   входящие `UC_ZJ55BR` («Необработанные ЛИДЫ») и `UC_PUCAAQ` («ОЖИДАЮТ
   СПЕЦИАЛИСТА»), целевая `NEW` («В РАБОТЕ»). Совпадения одного названия
   недостаточно — важен именно ID. При любом расхождении остановите деплой,
   исправьте константы и увеличьте `ROUTING_POLICY_VERSION`.
7. IT должен проверить права нового webhook на фактически используемые REST-
   методы: `user.get`, `crm.deal.list`, `crm.deal.get`,
   `crm.timeline.comment.list`, `crm.activity.list`, `batch` и, для сделки с
   OpenLine-сессией, `imopenlines.session.history.get`. Локальное приложение
   должно разрешать `user.current` для проверки вошедшего пользователя. Ошибка
   доступа к обязательному источнику сообщений намеренно блокирует выдачу, а
   не превращается в «сообщений нет». Право `crm.deal.update` проверяйте только
   на согласованной тестовой сделке непосредственно перед включением записи.
8. В Railway -> Service -> Source проверьте правильный репозиторий и production-
   ветку `main`; feature-ветка не должна автоматически заменять production.

Замена `managers.json` очищает только текущую версию файла, но не старые Git
commits и уже созданные clones. Если в публичной истории были реальные данные
сотрудников, их полное удаление — отдельная согласованная процедура GitHub с
переписыванием истории и уведомлением всех разработчиков; не делайте force-push
в одиночку.

### 2. Volume и масштабирование

1. Подключите к сервису один Railway Volume.
2. Mount path: `/data`.
3. Проверьте, что используется одна реплика. Railway не разрешает replicas для
   сервиса с Volume, а SQLite нельзя писать из нескольких контейнеров.
4. Включите автоматические backups Volume.

Railway монтирует Volume с владельцем root. Поэтому entrypoint кратко стартует
с root через Railway-переменную `RAILWAY_RUN_UID=0`, создаёт/проверяет `/data`,
исправляет владельца только известных файлов и запускает само приложение как
системный пользователь `bitrix` с UID/GID `10001`. Без Railway override образ
по умолчанию также запускается как `bitrix`. Рекурсивного `chown` по Volume нет.
Railway сам добавляет `RAILWAY_PROJECT_ID`, `RAILWAY_VOLUME_NAME` и
`RAILWAY_VOLUME_MOUNT_PATH`; не создавайте эти переменные вручную. Readiness
проверяет, что сервис действительно распознан как Railway deployment, Volume
подключён и его mount path точно совпадает с `APP_DATA_DIR`.

Если на старом Volume уже лежит `managers.json` с реальными сотрудниками, не
удаляйте его до backup и проверки `UF_SKILLS`. После успешного read-only
перехода замените активный файл отключённым placeholder из этого репозитория, а
нужный архив храните отдельно по согласованному IT сроку. Приложение не стирает
старый файл автоматически, чтобы не разрушить возможность расследования или
контролируемого rollback.

### 3. Variables

Добавьте все значения из `.env.example`. Критичные production-значения:

| Переменная | Production-правило |
|---|---|
| `BITRIX_WEBHOOK_BASE` | Новый секретный HTTPS webhook |
| `BITRIX_ALLOWED_DOMAINS` | Точный hostname портала, без `https://` |
| `PUBLIC_APP_URL` | Канонический HTTPS URL сервиса |
| `APP_ALLOWED_ORIGINS` | Только точные доверенные HTTPS origins, без `*` |
| `ADMIN_USER_IDS` | Реальные Bitrix ID администраторов в Railway, не в Git |
| `APP_DATA_DIR` | `/data` |
| `RAILWAY_RUN_UID` | `0`; entrypoint затем сам сбрасывает привилегии |
| `STATE_DB_FILENAME` | `state.sqlite3`, только имя файла |
| `CLAIM_STATS_SOURCE` | `app_events` |
| `REQUIRE_LEGACY_MIGRATION` | `1` для переноса этой действующей системы |
| `REQUIRE_EXPLICIT_ACCESS_RULE` | `1`; неизвестный сотрудник запрещён по умолчанию |
| `DRY_RUN` | `1` на первом деплое |
| `BITRIX_CLAIM_MARKER_FIELD` | код отдельного строкового UF-поля сделки до `DRY_RUN=0` |
| `GREETING_AUTO_SEND` | `0` на первом деплое; `1` только после controlled OpenLine smoke |
| `GREETING_WORKER_POLL_SECONDS` | `1`; задержка запуска фоновой очереди приветствий |
| `ALLOW_UNVERIFIED_USERS` | всегда `0` в Railway |
| `EXTRA_CLAIM_REQUESTS_ENABLED` | сначала `0`; включить только вместе с backend «Базы» |
| `BAZA_API_BASE_URL` | HTTPS origin backend «Базы», без пути и завершающего `/` |
| `BAZA_HMAC_KEY_ID` | идентификатор отдельного интеграционного ключа |
| `BAZA_HMAC_SECRET` | отдельный случайный секрет не короче 32 байт |
| `MAX_BITRIX_RESPONSE_BYTES` | `5242880`; oversized Bitrix/OpenLine JSON отклоняется до разбора |

Не добавляйте токен webhook в `PUBLIC_APP_URL`, frontend-конфиг, README или
логи. Не используйте wildcard в allowlist.

### 4. JSON -> SQLite migration

При первом старте `state_store.py` ищет в `/data` старые файлы:

- `access_rules.json`;
- `claim_log.json`;
- `reject_log.json`;
- `greeting_log.json`.

Для этой действующей системы с `REQUIRE_LEGACY_MIGRATION=1` должны одновременно
присутствовать **ровно все четыре** файла (пустые `[]`/`{}` допустимы). Неполный
набор считается ошибкой и ничего не импортируется. События должны содержать
непустые `managerId`, `dealId` и корректный ISO-8601 `timestamp` с часовым
поясом; исходное время события сохраняется. Все четыре файла проверяются и
импортируются одной SQLite-транзакцией. Только после полного успеха записывается
marker `legacy_json_migration_v1`. Исходные JSON не удаляются, не
переименовываются и не перезаписываются — это страховка для аудита и отката.
Marker сохраняет SHA-256 каждого исходного файла; при последующих стартах
изменение, удаление или подмена любого retained JSON останавливает readiness,
чтобы старая JSON-версия не создала незаметно расходящуюся историю.

Если хотя бы один присутствующий JSON повреждён или имеет неверный формат:

- частичного импорта нет;
- migration marker не ставится;
- `/api/ready` возвращает 503;
- Railway не активирует новый deployment.

Исправьте или восстановите JSON из backup и перезапустите deployment. Не
создавайте пустой JSON поверх повреждённого. Для действительно новой установки
без legacy JSON явно задайте `REQUIRE_LEGACY_MIGRATION=0`; тогда создаётся
чистая БД и readiness остаётся успешным. При значении `1` отсутствие manifest
намеренно оставляет readiness в состоянии ожидания migration.

Если legacy-файлы ещё не находятся на подключённом Volume, сначала остановите
автодеплой/оставьте сервис read-only, загрузите файлы через Railway Volume
browser/CLI и только затем перезапустите migration. Не вставляйте содержимое
журналов в issue, PR или чат.

Для этой действующей системы оставьте `REQUIRE_LEGACY_MIGRATION=1`: readiness не
пропустит ни одной новой записи, пока migration marker не станет `completed`.
Только действительно новая установка без прежней истории может явно поставить
`0`.

### 5. Readiness и smoke test

Railway проверяет `/api/ready`. Разница endpoint-ов:

- `/api/health` — процесс жив; ответ минимальный и не доказывает готовность;
- `/api/ready` — конфигурация, allowlist, поддерживаемый stats mode, доступная
  SQLite и завершённая/не требующаяся migration готовы. Успех: HTTP 200;
  проблема: HTTP 503 с безопасным кодом причины без токенов и персональных
  данных.

Сервис с Volume не может держать старый и новый deployment одновременно на
одном диске. Readiness не пропустит неисправную версию в Active, но при неудачной
migration возможен короткий простой до исправления или rollback.

После deployment, пока `DRY_RUN=1`:

1. В карточке deployment сравните commit SHA с проверенным merged commit PR.
2. Откройте `/api/ready` и убедитесь, что HTTP 200.
3. Проверьте логи: нет migration/config/database errors, приложение запущено
   после entrypoint от UID 10001.
4. Через временное тестовое локальное приложение/placement, handler которого
   указывает на новый `PUBLIC_APP_URL`, откройте сервис внутри Bitrix24 под
   обычным менеджером. Он должен определить именно вошедшего пользователя;
   переданный вручную чужой ID не должен менять личность. Если отдельное
   тестовое приложение создать нельзя, выполните контролируемое переключение
   основного handler при сохранённых `DRY_RUN=1` и плане немедленного возврата.
5. Откройте под администратором и проверьте read-only статистику.
6. Проверьте, что запрос с посторонним Origin и OAuth domain отклоняется.
7. Нажмите сценарий получения заявки и подтвердите в Bitrix24, что ответственный,
   стадия и сообщения не изменились.

Только после этой проверки IT оставляет основной handler/install URL локального
приложения Bitrix24 на новом `PUBLIC_APP_URL`; при провале возвращает прежний
URL. Когда новый read-only deployment проверен, решение о rollback принято и
переключение подтверждено, отзовите старый webhook в Bitrix24 и ещё раз
проверьте `/api/ready` и вход под менеджером.

### 6. Отдельное включение записи

Запись — отдельный релизный шаг, а не часть первого деплоя:

1. Сделайте свежий Volume backup.
2. Получите явное бизнес-подтверждение на смену ответственного и стадии.
3. IT создаёт в сделке отдельное строковое UF-поле-маркер и указывает его код
   в `BITRIX_CLAIM_MARKER_FIELD`. Маркер записывается тем же обновлением, что
   ответственный и стадия; по нему журнал восстанавливается даже после crash.
4. До включения записи IT должен обеспечить правило: переход из входящих стадий
   в `NEW` выполняет только это приложение. Публичный Bitrix REST не даёт
   условного atomic update «изменить, только если стадия всё ещё прежняя»;
   параллельный ручной переход или робот иначе может попасть в гонку между
   серверной проверкой и записью. Если ручные переходы нужны, требуется
   отдельный Bitrix workflow/lock, согласованный IT.
5. Поменяйте только `DRY_RUN=0`; пока оставьте `GREETING_AUTO_SEND=0`.
6. На одной тестовой сделке проверьте: один claim event, правильный
   ответственный, правильная стадия и корректный ответ при повторном нажатии.
7. На отдельной тестовой сделке поставьте `GREETING_AUTO_SEND=1` и повторите
   claim: карточка должна открыться сразу, менеджер должен принять OpenLine через
   `imopenlines.operator.answer`, а одно приветствие — появиться от его имени
   через `im.message.add` в чате выбранной сессии.
8. При timeout после начала отправки outbox ставит `uncertain` и не повторяет
   сообщение автоматически: это защищает клиента от дубля. Чат проверяет
   администратор и при необходимости отправляет текст вручную.

## Эксплуатация

- Относительные даты считаются с `APP_TZ_OFFSET_HOURS=6` (Бишкек).
- Дневной лимит менеджера не действует по воскресеньям и в локальном интервале
  от `LIMIT_FREE_WINDOW_START` включительно до `LIMIT_FREE_WINDOW_END` не
  включительно. Переменные меняют только время; отмена воскресного исключения —
  изменение кода и требует bump `ROUTING_POLICY_VERSION`.
- Не увеличивайте лимиты и cache bounds без замеров: они защищают сервис и
  Bitrix24 от перегрузки.
- `READINESS_CACHE_TTL_SECONDS` сериализует и ненадолго кэширует проверку БД,
  чтобы публичные health probes не запускали параллельные integrity scans.
- Railway deployment healthcheck выполняется при выпуске, а не является
  постоянным мониторингом. Для production нужен отдельный uptime monitor на
  `/api/ready` и алерт по 5xx.
- Делайте регулярные Volume backups и периодически проверяйте восстановление в
  отдельном окружении.
- Не копируйте `state.sqlite3` из работающего процесса обычным файловым copy:
  используйте Railway Volume backup или согласованный SQLite online backup.
- Не удаляйте legacy JSON сразу после migration. Срок хранения определяет IT
  после сверки количества событий и правил.
- SQLite-журнал намеренно не обрезается автоматически: удаление старых claim,
  reject или greeting событий без утверждённого срока хранения разрушит аудит.
  IT должен мониторить размер `state.sqlite3`/Volume и согласовать срок хранения,
  экспорт и архивирование персональных данных до любого prune.

## Rollback

Railway rollback восстанавливает старый образ и сохранённые для deployment
variables, но не откатывает содержимое Volume. Поэтому откат к старой
JSON-версии не должен продолжать запись: она не увидит новые SQLite-события и
создаст две расходящиеся истории.

Безопасный порядок:

1. Поставьте `DRY_RUN=1` и `GREETING_AUTO_SEND=0`.
2. Создайте новый backup текущего Volume.
3. Если новый deployment не прошёл `/api/ready`, Railway пометит его неуспешным.
   Из-за эксклюзивного Volume может быть простой: исправьте причину или сразу
   откатите проверенный deployment.
4. Если активный релиз нужно срочно откатить, в Railway откройте
   **Service -> Deployments -> ... -> Rollback** у последнего проверенного
   deployment.
5. После rollback оставьте приложение read-only, проверьте `/api/ready`, логи и
   Bitrix24.
6. Не удаляйте `state.sqlite3`, journal/WAL/SHM или legacy JSON. IT должен отдельно
   сверить события и выбрать roll-forward либо контролируемое восстановление
   Volume backup.

Предпочтителен roll-forward: исправить код, пройти CI/readiness и снова
развернуть совместимую SQLite-версию. Это сохраняет единый журнал событий.
